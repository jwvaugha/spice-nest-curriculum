## Build history

The user asked for this to be "fully MUI/React enabled" so it actually relates to the Figma designs (which are themselves built from a connected MUI component library — see below) rather than hand-approximated CSS, plus a global nav that spans the entire viewport width, plus a from-scratch color-token audit against the Figma file directly (some of the `Web Prototype/` build's guessed values were wrong). `Web Prototype/` was **not deleted** — it's kept as a simpler reference — but new work happens here.

- **Stack**: Vite + React 19 + `@mui/material` v9 + `@mui/icons-material` + `react-router-dom` v7. `npm run dev` from inside `nest-react-app/`.
- **The Figma file's components genuinely are MUI**, confirmed via `figma.teamLibrary.getAvailableLibraryVariableCollectionsAsync()`: it's connected to two libraries literally named "SPICE Education Project MUI Variables + Style" and "Spice Phase 3 MUI", with collections named `Palette`/`Typography`/`Semantic Name`/`Sizes` — i.e. this design system was built to mirror an MUI theme object 1:1, not just visually resemble one. `src/theme.js`'s structure (`palette.primary/secondary/text/background`, `typography.h1-h6`) intentionally follows that same shape.
- **Full color-token audit, not spot-checks**: swept every `fills`/`strokes` bound-variable across the entire "Nest - Local Components V2" page plus the Dashboard/Mod-2-Ch-2/Mod-1-Ch-5 frames themselves (26 distinct variables actually in use), resolving each alias chain to its final RGB value via `figma.variables.getVariableByIdAsync`. **This caught real errors in the earlier plain-HTML build** — most notably `Global/dividerColor` is `SPICE-Edu-Neutral-B/200` = `#c8bfb6` (a visibly more saturated warm gray), not the paler `#e9e1d8` that had been guessed from a screenshot. Full token table with Figma provenance is in `nest-react-app/README.md` and `theme.js`'s own comments. Caveat for next time: the workspace also has a large generic MUI Material color palette (`Red/600`, `Blue/300`, etc. — literally `@mui/material/colors`, ~300 entries) and a second, apparently-unused generic teal-based semantic theme (`theme/primary/color` lowercase → `emerald/500`) living in the same library — **don't pull colors from library-collection dumps by name alone**; always verify a variable is actually bound to a fill/stroke somewhere in the real design before trusting it, since the library contains dead/unused alternate themes alongside the real one.
- **Global nav spans the full viewport width**: `GlobalHeader.jsx` (an MUI `AppBar`) is rendered in `App.jsx` *outside* any `Container`/max-width wrapper — full-bleed edge to edge — while each page's own body content sits inside its own `Container maxWidth="lg"` below it. If a future page's content also needs to be full-bleed, do NOT wrap the header in the same container as the body; keep them structurally separate the way `App.jsx` already does.
- **MUI v9 breaking-change gotchas hit during this build** (see `nest-react-app/README.md` for the full note): `Stack`/`Grid` dropped `alignItems`/`justifyContent` as direct props — they silently leak onto the DOM as invalid attributes now (console warning, styling just doesn't apply) — use `sx={{alignItems, justifyContent}}` instead. `ListItemText`'s `primaryTypographyProps`/`secondaryTypographyProps` were removed for `slotProps={{primary: {...}, secondary: {...}}}`. Both were caught only by actually screenshotting the rendered page and cross-checking the dev-server console log, not by the code merely compiling — **always render-and-check a real MUI major-version upgrade's prop surface rather than trusting prior MUI knowledge**, since this version is newer than most existing documentation/training assumes. **A second, more serious manifestation of the same `Stack` `alignItems`-as-prop no-op surfaced 2026-09-30**: `StickyAsideSection.jsx`'s row `Stack` used `alignItems="flex-start"` as a direct prop, which silently did nothing — the row's default `align-items: stretch` then stretched the sticky aside box to match its much taller sibling's full height, and a sticky element that's exactly as tall as the space it would otherwise scroll through has nowhere to actually detach from the flow, so `position: sticky` visually behaved as if it weren't set at all (the label scrolled in exact lockstep with the page). Confirmed via direct measurement (`getBoundingClientRect().top` at increasing scroll offsets moved in lockstep with the prop, then clamped to a fixed value once fixed via `sx`) — **this is the reason to actually verify sticky/stretch-sensitive layouts by measuring, not just eyeballing a screenshot**: a stretched-but-still-technically-`position:sticky` element can look identical to a correctly-sticky one in a single static screenshot taken before any scrolling happens.
- **Radio-accordion and "viewed" persistence work exactly as in the plain-HTML build**, just via real MUI `Collapse` + a shared `useViewedChapters` localStorage hook instead of vanilla JS — see `src/hooks/useViewedChapters.js`. Both the Dashboard's inline Module 2 chapter list and each chapter page's own sidebar read from the *same* hook, so viewing a chapter from either location clears its dot everywhere consistently (the plain-HTML build had a bug here — Dashboard's dot logic didn't match the sidebar's — fixed in this rebuild).
- Images: same drop-in-a-file convention, copied into `public/images/` (Vite serves `public/` at the site root, so `public/images/module-2-chapter-2/hero.jpg` → `/images/module-2-chapter-2/hero.jpg`).
- **`ChapterMenuItem.jsx` was rebuilt as one cohesive component after a second round of user feedback (2026-09-19)** — an earlier version styled the header (a `ListItemButton`) and the expanded section list (a separate `List`) independently, which caused exactly the bugs you'd expect from treating one logical item as two: the active-row background tint and the left accent bar only covered the header, not the expanded content beneath it, because the header's own opaque background painted over the bar for that region while the (transparent) collapsed content let it show through — so the bar looked like it only existed for the sub-content. Fixed by moving every whole-item visual (background tint, hover, the accent bar, the outer border) onto ONE outer container, with the header rendered as a bare `ButtonBase` (no competing background of its own) and the `Collapse`'s `List` also background-less, so the outer container's styling shows through uniformly across header + expanded content. **The active-row tint's exact value was wrong too** — swept it directly off the Figma node rather than eyeballing: it's a flat `SPICE-Edu-Orange/700` at 4% opacity (`rgba(222,122,45,0.04)`) applied to the *entire* component (header + section rows, confirmed same fill at full height on the actual node), not a distinct light-cream token. **General lesson**: when a component has an "active/selected" or "expanded" state that visually spans header+content together, style it that way from the start — a header-styled-separately-from-content split will keep resurfacing the same class of bug (background, hover, borders, accent bars all needing to be kept in sync by hand) rather than being structurally impossible to get out of sync.
- **Typography letter-spacing/line-height corrected against the real bound Figma text styles (2026-09-19)**, not eyeballed: `Typography/H4` (chapter hero title) is Vollkorn Regular 40px, **-5% tracking** (→ CSS `-0.05em`), 123.5% line-height; `Typography/H5` (Section Title) is Vollkorn SemiBold 28px, **-0.5px tracking** (a literal px value, not a %, so it does NOT scale with font-size), 133.4% line-height; `Typography/H6` is **Roboto SemiBold, not Vollkorn** — this was a real bug, the H6 MUI variant had been set to a serif font — 18px, **+10% tracking** (→ `0.1em`), 160% line-height. `h3` wasn't individually swept (no chapter needed it checked) — given a small consistent tracked-in value as a reasonable interpolation between the two confirmed Vollkorn figures, not asserted as exact. **Gotcha for reuse:** MUI's `variant="h6"` was also being reused for the Sidebar's Module Header Card title (a *different* Figma component that happens to also be a serif heading) — fixing the shared `h6` theme variant to match the real "H6 Subtitle" component would have silently broken that unrelated usage, so it was decoupled into its own explicit inline style instead. Don't assume two things sharing an HTML-semantic variant name in code are the same Figma component.
- **Sidebar section links are only real for the currently-active chapter.** `ChapterMenuItem`'s `sections` prop accepts either plain strings (a preview-only label, rendered as static text — used for every *other* chapter's row, since their content doesn't exist on the page you're currently looking at) or `{label, id}` objects (rendered as a real clickable link that scrolls the matching `id="..."` element on the page into view — used only for the active chapter's own sections, the one case where "jump to this part of the chapter" is actually honest). Don't make a non-active chapter's preview sections clickable — there's nothing on the current page for them to scroll to.
- **Two chapters (Module 1 Ch 4 "The Nutrition Facts Label", Module 2 Ch 3 "Why are South Asians at greater risk of diabetes?") have no real section content anywhere** despite the CSV roadmap marking Ch4 "Complete" — verified by searching the CSV, every Word-doc folder, and the entire Figma Deliverable page; nothing exists for either (Ch3 is also tagged Type=Video in the CSV, not Text, so it wouldn't get a text outline regardless). Their sidebar rows correctly stay on `Expand=None` (no chevron, no fabricated sections) until real source material shows up — don't invent section titles for these just because a tracker says "Complete."
- **Audit pass (2026-09-19) against fresh Figma screenshots caught real, fixed gaps** — worth re-running this exact exercise (screenshot both sides, compare directly) after any future substantial change, since several of these were invisible from code review alone: the header logo was a placeholder "+" instead of the real two-path SVG brand mark (now `src/assets/spice-logo-mark.svg` / `LogoMark.jsx`, pulled via `download_assets`); "SPICE-Healthcare" was wrongly force-uppercased and "Jane Doe" wasn't (Figma does the opposite for each); Module 2's sidebar header used the long module description instead of the real short subtitle "Diabetes Care"; only the currently-active chapter had a working expand/collapse section list — Figma gives that to *every built chapter* in the sidebar, so Chapters 1/4/5 (Mod 2) and 1/2 (Mod 1) needed their real harvested section lists added too; the unviewed dot is a small badge on the icon's top-right corner in Figma, not a separate dot floating after the row text; the dot's coverage rule is simply "every non-active row, cleared only if actually visited" (including resource rows with no page, which just never clear) — not the narrower hardcoded per-chapter list originally guessed; the selected-row tint was MUI's default `action.selected` gray instead of the real accent tint (`SPICE-Edu-Neutral-A/25`, now set properly in `theme.js`); and the footer button said "Back to Dashboard" instead of Figma's constant "CONTINUE TO NEXT CHAPTER" (which never changes label even when — as here, with only 2 standalone pages — it can only actually go to the Dashboard) — fixing this also caught a real functional bug where the footer button never actually called `markChapterViewed` at all.
- **App-shell layout rework (2026-09-19/20), Coursera/LinkedIn-Learning-style**, replacing the earlier "single scrolling page" model: `GlobalHeader` (sticky, `HEADER_HEIGHT`=64px) and `DashboardBackLink` (sticky right below it, `BACKLINK_HEIGHT`=48px, full-width bar with an inset clickable link — same pattern reused for `ChapterFooter`) are the only page-level scroll; below them, each page is a fixed-height row (`calc(100vh - bars)`) split into `Sidebar`/`DashboardDrawer` (flush left, fills the row's full height, own independent scroll, no more floating bordered card) and a content column that is itself scrollable body + a `ChapterFooter` permanently pinned at the bottom (never scrolled away — this is what makes "next chapter" read as an always-visible footer instead of a scroll-to-the-end link). Shared height constants live in `src/layoutConstants.js`; if either bar's real rendered height changes, update the constants or the row-height math drifts. Removing the old floating card's full border to go flush-left also removed the depth cue that separated its near-white bg from the near-white page bg (`background.paper` #ffffff vs `background.default` #fffdfa were always this close — not a color regression) — restored via a subtle right-edge `boxShadow`, not a new color.
- **Cascading content widths, deliberately NOT one column** (`layoutConstants.js`: `HERO_WIDTH`=872 outer canvas → hero image renders ~808 after the canvas's own 32px×2 padding, `PHOTO_MAX_WIDTH`=720, `TEXT_MAX_WIDTH`=600, all centered on the same axis). Rule for which tier a photo gets: **a photo inside a list row (`NumberedListItem`) obeys the row's own `TEXT_MAX_WIDTH`** — matching Figma, where a List Item's image never outgrows its row — **while a standalone, non-list photo (`MythFactCard`) is allowed to span wider at `PHOTO_MAX_WIDTH`**, since it's presented as its own editorial block, not a compact row. Don't set width constants against the *nominal* canvas figure (872) — a component nested inside the canvas's own padding sees the *effective* ~808px, so anything sized close to 872 reads as visually identical to the hero instead of "a bit smaller."
- **`NumberedListItem`'s number badge sits in-row, inside the same `TEXT_MAX_WIDTH` box as the section heading — never hung outside it.** A brief intermediate version tried a hanging indent (`position:'absolute', left: -(badge+gap)`, relying on leftover canvas gutter space to the badge's left) to satisfy "numbers read as less indented than the content." That gutter shrinks with the viewport and hits zero on a narrow window, clipping the badge against the scroll pane's `overflowX:hidden` — a real bug. Fixed back to a normal `Stack direction="row"` (badge + text both inside the `TEXT_MAX_WIDTH` box, badge `flexShrink:0`): the whole row (badge indent included) is never wider than the content column, robust at any width, and the badge still reads as "less indented than the content" simply because it comes first in the row, before the text.
- **`useSettledWidth` hook (`src/hooks/useSettledWidth.js`) — a true debounce, not a CSS transition**, for the reading column's own width during a live window resize. The scrollable pane still resizes instantly via plain CSS flex; only the inner content canvas's pixel width (measured via `ResizeObserver`) waits ~200ms after resizing stops before committing a new value, so body text doesn't rewrap on every intermediate drag pixel — it snaps once, when the resize settles. The pane needs `overflowX:'hidden'` as a safety net for the brief window where the frozen width can exceed a shrinking pane before the debounce fires.
- **`theme.typography.h6` has `textTransform:'uppercase'` baked in directly** (not a per-instance `sx` override) — this is the real Figma "H6 Subtitle" style (confirmed on the component node), used for eyebrows (`ChapterHero`), Myth:/Fact: labels (`MythFactCard`), and list-item titles like "Refined Carbohydrates" (`NumberedListItem`). Baking it into the theme once caught a real inconsistency: 3 of 4 h6 usages had manually re-added `textTransform:'uppercase'` per-instance, but `NumberedListItem`'s title never did, so it was quietly rendering in sentence case. `DashboardDrawer`'s "NEST" heading also uses `variant="h6"` but is a different, deliberately-decoupled Figma component (serif, its own inline font override) — its literal text happens to already be typed in caps, so the shared uppercase transform doesn't visibly affect it, but don't assume that'll always be true for a future h6 usage with mixed-case text that isn't meant to be shouted.
- **`Reference.jsx` — standard element for every References section, replacing the old plain `<ul><li>` bullet rendering.** Mirrors Figma's "Reference" component (node `3182:14767`: a single `SPICE-Edu-Neutral-A/25` rounded card, 16px radius/padding, Roboto Regular 16px/150%/+0.15px tracking, `Global/textPrimary`) — but adds the one thing a static Figma design can't do: any `http(s)` URL inside the citation text is detected and rendered as a real, underlined, clickable MUI `Link` (trailing sentence punctuation like a closing period/comma is kept out of the `href`), while citations with no URL render as plain text with no fabricated link. Used via `<Stack spacing={1.5}>` of `<Reference>` items inside the same `TEXT_MAX_WIDTH` wrapper as the rest of a section's body text — References are prose-like content, not a "standalone photo," so they don't get the wider `PHOTO_MAX_WIDTH` tier.
- **`theme.js` `fontSize` values must stay `rem` strings, never bare numbers** — a Cursor edit switched `h1`/`h2`/`h6` to plain px numbers (`32`/`24`/`16`) while also shrinking `h2`/`h6`; reverted the units back to `rem` (`'2rem'`/`'1.5rem'`/`'1rem'`) while deliberately keeping the new, smaller sizes — bare-number `fontSize` doesn't scale with a user's browser font-size/zoom preference the way `rem` does, a real accessibility regression even though it renders identically at default zoom.
- **A list item's photo lives INSIDE the same `flex:1` text column as its title/description** (a sibling after the paragraph, not a separately-centered `TEXT_MAX_WIDTH` block) — so it's automatically exactly as wide as, and left-aligned with, that specific paragraph, not the full badge+text row. This is a refinement of the "list photos obey `TEXT_MAX_WIDTH`" rule above: obeying the row's width isn't enough on its own, since the row = badge + gap + text, and centering the photo across that whole row still left it wider/shifted vs. the paragraph text a reader would associate it with.
- **`NumberedListItem` takes optional `tip`/`tipLabel` props**, rendered as a `TipExample` callout after the image (Figma's "Serving Size Examples" pattern, e.g. Mod-1-Ch-2's food groups). `TipExample.jsx` mirrors Figma's "Tip-Example" component (yellow card, overlapping type-badge pill at the top-left) — flat header bar only, no expand affordance, consistent with the standing convention that every instance built so far ships collapsed with nothing behind it to reveal.
- **`Module1Chapter2.jsx` (Food Groups) built from Figma node `3457:29392`** — the first nest-react-app page ported directly from a Figma node rather than hand-authored from Word-doc/Deliverable content. Images: `download_assets` on the whole page node returned 14 raw images for what should have been 7 (hero + 6 food groups) — every real photo existed as an **exact duplicate pair** (same subject, re-uploaded/re-encoded twice), not 14 unique images; built a contact-sheet thumbnail grid to identify the 7 unique subjects by eye and picked one file per pair, rather than guessing from download order or trying to match nested composite instance IDs (`download_assets`'s `nodeId` param only accepts simple `123:456` IDs, not the `I123:456;789:012;...` composite IDs a deeply-nested instance actually has — the whole-page-node download + visual dedup was the workaround). Resized to ~1600px/82%-quality JPEGs via `sips` before committing to `public/images/module-1-chapter-2/` (originals were 2-4.7MB PNGs/JPEGs).
- **`ChapterMenuItem` now supports a row that both navigates (`to`) AND has its own togglable preview section list (`sections`)** — previously these never coexisted (only one chapter per module was ever a real built page, so a `to`-having row never also carried real `sections`). Now that Module 1 has two real cross-linking chapters (Ch2, Ch5), clicking a sidebar row's main body navigates via `Link` while the chevron is a separate sibling `ButtonBase` (not nested inside the Link — HTML forbids interactive-in-interactive) that independently toggles the preview list via `stopPropagation`. A row with `sections` but no `to` still just toggles on click, same as before.
- **Sidebar chapter-title weight/icon color, both verified against real Figma nodes, not eyeballed**: title is `fontWeight: 400` (Regular) for a non-active row, `500` (Medium) for the active one — was wrongly `500`/`600`. Icon glyph color is `#a69889` (`Global/iconInformational`, confirmed via direct fill inspection on the "Chapter Icon" component, node `2995:14162`) — was wrongly `primary.dark` (too dark/saturated). The unviewed-chapter dot was also off by one Figma variable (`#de5f2d` guessed vs. the real bound `Theme/Primary/Main` `#de7a2d` = `theme.palette.primary.main`) — now references the theme token directly instead of a hardcoded near-miss hex.
- **`Sidebar` default width is 308px (Figma's real "Sidebar" component, node `3139:13139`), not 320** — 320 had been an unverified round-number guess. Checked `DashboardDrawer`'s equivalent component ("Dashboard Nav Drawer", node `3445:13283`) directly too before assuming it should match: that one genuinely IS 320px in Figma, so the two intentionally differ — don't "fix" `DashboardDrawer` to 308 by analogy.
- **`getContentPaddingX(panelWidth)` (`layoutConstants.js`)** — the content canvas's horizontal padding (the margin between the chapter content column and the content panel's own left/right edges — the panel being the area right of the module sidebar, above the chapter footer) *grows* from `BASE_PADDING_X` (32px) to `NARROW_PADDING_X` (48px) once the panel itself is narrower than `HERO_WIDTH`. **First attempt at this used a static MUI breakpoint object (`{xs:6, sm:5, md:4}`) keyed to the global viewport width — wrong, because the panel is already narrower than the viewport by the sidebar's width (308px), so a viewport-keyed breakpoint fires at the wrong moment relative to when the panel itself actually starts constraining content.** Fixed to compute padding directly from `useSettledWidth`'s measured panel width (`panelWidth < HERO_WIDTH` = the canvas is no longer capped by its max-width and is actively shrinking to fit — exactly the moment more breathing room is wanted). `RESIZE_TRANSITION` now animates `padding` alongside `width` so this step change animates in too, not just the width settle.
- **Paragraph line-height is scaled by a shared percentage factor, not set to a fixed value** — `theme.js` exports `LINE_HEIGHT_SCALE` (1.06, "+6%") and multiplies it against each paragraph variant's own MUI default (`body1`: 1.5→1.59, `body2`: 1.43→1.516) rather than normalizing both to one number, preserving MUI's own relative rhythm between them. `Reference.jsx` (a plain `Box`, not a `Typography` variant, so it doesn't inherit theme values automatically) imports the same constant rather than hardcoding its own scaled number, so the two can't drift independently. Headings are untouched — this only applies to paragraph-style text.

- **`get_design_context` can't render content clipped by the prototype's fixed-height Content Panel** (`clipsContent:true`, `overflowDirection:'VERTICAL'`, per the Interactive Prototype section below) — it errors `"invalid node selection... select a node from a visible page on the canvas"` on any node below the ~664px fold, even though `get_metadata` and direct `use_figma` reads work fine on the same nodes (they operate on the document model, not rendered pixels). Workaround used for `Module3Chapter2.jsx`: `get_metadata` for structure, then targeted `use_figma` scripts recursively walking each section by node ID to pull real text content (`node.characters`) and image fill hashes directly — no file mutation needed. - **Spacing-architecture audit (2026-09-20) — "slot" components now own their own gap values, matching Figma's actual architecture, not just centralized numeric constants.** Every page had been hand-picking its own `mb`/`Stack spacing` per element (`mb:1, 1.5, 1.75, 2, 2.5...` scattered per page/section), when the real Figma ground truth — swept directly off the live component definitions on the Nest V2 page (`itemSpacing`/padding read via the Plugin API on the actual components, not one instance's possibly-overridden geometry, not eyeballed) — is:
  - **Section (Slot)**: `pt:24, pb:32`, `itemSpacing:32` (title → content) — was wrongly a symmetric `py:4` (32/32) everywhere.
  - **Content Slot**: `pl:20` (indents content vs. its own section title — was missing entirely on every page), `itemSpacing:32` **uniformly between every direct content child** — heading → paragraph → bulleted list → image alike, ONE flat gap, not a tighter "heading to its own paragraph" special case. This includes `Reference` cards: they're flat Content Slot children too, so consecutive References get the same 32px gap, not a separate tighter 12px `Stack` (a real, pervasive bug fixed by this audit).
  - **List Slot**: `itemSpacing:40` between List Items — one page used 28px, this constant fixes it everywhere at once.
  - **List Item**: `itemSpacing:20` (badge → content, already correct), **`pb:24` baked into the item itself** — a SEPARATE value from List Slot's 40, composing to a real ~64px total gap between items (two genuinely distinct numbers in the live component tree, not one counted twice).
  - **Item Content Slot**: `pt:8`, `itemSpacing:24` (title/paragraph/image within ONE list item — already correct pre-audit).
  - **Bulleted List Slot**: `itemSpacing:12` (already correct pre-audit).
  - **Paragraph/Body Normal's own internal label→body gap**: `12px` — confirmed by checking the actual node tree that Mod-3-Ch-2's "Day 1"/"Cook roasted chicken..." are the `Section Label` and body text of ONE Paragraph/Body Normal instance (Show Label=true), not two separate Content Slot siblings — this distinction is why `Paragraph.jsx` exists as its own component rather than just reusing `variant="h6"` + a second `Typography` inline.
  
  **New reusable "slot" components, not just numeric constants** (deliberate choice, confirmed with the user — the whole point of a Figma "slot" component is that it owns its gap so every instance stays in sync automatically; centralizing only the numbers still lets a future page forget to import them and drift again):
  - `Section.jsx` — mirrors "Section (Slot)" exactly: owns `pt:24/pb:32`, the title→content 32px gap, the 20px content indent, and the uniform 32px gap between every child. A page just does `<Section id="..." title="...">{flat content children}</Section>` — never its own `mb`/`spacing` for inter-content gaps again. `sx` is an escape hatch for the one legitimate override: the first section on a page wants `pt:0` since `ChapterHero` already contributes its own trailing margin.
  - `NumberedList.jsx` — mirrors "List": owns the real 40px List Slot gap between `NumberedListItem` children.

## Fade-in-on-scroll (added 2026-10-01)

Every chapter page's content now reveals progressively as the reader scrolls, instead of all being present from first paint — per direct user request, with an explicit design goal of NOT animating every element individually (a long list shouldn't pop in item-by-item if its items are just short text, but a list of photo-bearing items reasonably could). The approved rule set, implemented as planned with no deviation:
1. **Default unit = the whole `Section`** (and `StickyAsideSection`, `ChapterHero`) — all of a section's prose (headings, paragraphs, short bullet lists, `Reference`/`TipExample`/`DesignNote` callouts) fades in together as one block the moment any part of it scrolls into view. This is the ONLY reveal most pages ever see — a text-only chapter (e.g. Mod-6-Ch-2) never gets per-paragraph animation.
2. **Escalate to an individual reveal only when a block is a genuinely substantial visual element**: a `NumberedListItem` gets its own reveal exactly when it carries a photo (`imageSrc`/`placeholderNote` — a single clean condition, not an item-count threshold); a plain-text item has no reveal of its own and just inherits whatever its ancestor `Section` already resolved to. `MythFactCard` and `ComparisonTable` always get their own reveal (every instance is inherently a substantial visual block).
3. **Nesting an item-level reveal inside a section-level reveal is safe and intentional, not redundant**: CSS opacity composes down the DOM tree, so a photo item's own `opacity:0` still holds even after its ancestor `Section`'s opacity has already resolved to 1 — the item just waits for its OWN intersection to fire. This is what lets Rule 1 and Rule 2 coexist with zero coordination code between the two levels.
4. **Fires once, ever** (`IntersectionObserver` unobserves itself on first intersection) — no re-fade scrolling back up past something already revealed. Content already in the initial viewport goes through the exact same path (the observer fires immediately if the element is already intersecting when `observe()` is first called) — there's no separate "already visible on mount" code path.
5. **Respects `prefers-reduced-motion`** — skips the animation and `useState` initializes straight to `visible: true` for users with that preference, verified via Playwright's `emulateMedia`.

Implementation: `src/hooks/useRevealOnScroll.js` exports the hook (returns `[ref, visible]`) plus a shared `revealSx(visible, delayMs)` sx-fragment helper (opacity + 16px translateY slide, 450ms ease-out) so every call site spreads the identical animation rather than re-typing it. **The observer's `root` must be explicitly set to the real scrolling ancestor, not left as the default (browser viewport)** — this app's chapter pages scroll inside their own nested `overflowY:auto` pane (see the App-shell layout rework entry above), and the default viewport-root would misfire (an element scrolled out of the pane's own visible area can still geometrically overlap the browser window, since it's the pane's content that scrolled, not the pane's own box) — same DOM-walk-up-to-find-the-real-scrolling-ancestor trick already used in `NutritionLabelExplorer`'s height measurement, reused here rather than threading a `root` prop down through every call site. `NumberedListItem` also applies a light stagger (70ms per position, capped at 5 steps) via the hook's `delayMs` param, so several photo items entering the viewport together cascade in rather than popping simultaneously. Wired into `Section.jsx`/`StickyAsideSection.jsx`/`ChapterHero.jsx` (whole-block, unconditional), `NumberedListItem.jsx` (conditional on `imageSrc`/`placeholderNote`), and `MythFactCard.jsx`/`ComparisonTable.jsx` (unconditional). **Known, deliberate scope boundary**: a handful of pages place a standalone photo directly as a raw `<Box component="img">` Section child (not via `NumberedListItem`) — these are left at Section-level batching rather than retrofitted with their own reveal, since doing so would mean introducing a new shared image-wrapper component and touching every page that uses the raw pattern, which wasn't asked for; they still fade in correctly, just as part of their Section's single block rather than escalating individually. Verified via Playwright on both a photo-heavy list page (Mod-1-Ch-2, confirmed per-item opacity 0→1 as each item's own image scrolls into view, and confirmed no re-fade scrolling back to the top) and a plain-text-only page (Mod-6-Ch-2, confirmed whole-section batching, zero per-paragraph animation) — plus the standing `full_verify.js`/`stress_dense.js` regression suite, both clean.
